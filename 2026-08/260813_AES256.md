AES-256-GCM 기반 안전한 양방향 암호화 모듈 구현

학습일: 2026.08.13
주제: OWASP A02 (Cryptographic Failures) 방어를 위한 대칭키 암호화 유틸리티 작성

데이터베이스에 저장될 민감정보(주민등록번호, 계좌번호 등)를 평문으로 저장하는 취약점을 방지하기 위해, Java Cryptography Extension (JCE)을 활용하여 AES-256-GCM 암호화 모듈을 구현했다.

1. 왜 GCM (Galois/Counter Mode) 인가?

암호화 알고리즘(AES)을 사용할 때는 데이터를 어떻게 쪼개서 섞을지 결정하는 '운영 모드'를 반드시 선택해야 한다.

ECB 모드 (금지): 동일한 평문 블록이 동일한 암호문으로 변환된다. 데이터의 패턴이 그대로 노출되므로 실무에서 절대 사용해서는 안 된다.

CBC 모드 (취약): 이전 블록의 암호문을 다음 블록에 섞어 패턴을 숨긴다. 하지만 데이터의 기밀성만 보장할 뿐 '무결성'을 보장하지 못해 Padding Oracle 공격 등에 취약하다.

GCM 모드 (채택): 현재 실무 표준으로 사용되는 AEAD(인증된 암호화) 모드다. 데이터를 암호화함과 동시에 '인증 태그(Authentication Tag)'를 생성하여 결합한다. 복호화 시 이 태그를 검증하므로, 해커가 암호문을 단 1비트라도 변조하면 복호화 과정에서 즉각적으로 예외(AEADBadTagException)를 발생시켜 공격을 차단한다.

3. 핵심 보안 포인트 (회고)

단순히 구글링한 코드를 복사해서 쓰는 것을 넘어, 동작 원리를 명확히 분석하고 적용했다.

무작위 IV(초기화 벡터) 사용: 동일한 비밀번호를 두 번 암호화하더라도 매번 다른 암호문이 나와야 안전하다. 이를 위해 암호화 메서드가 호출될 때마다 SecureRandom을 이용해 12바이트 크기의 난수 IV를 새로 생성하도록 구현했다.

IV와 암호문의 결합 저장: 복호화를 하려면 암호화할 때 사용했던 바로 그 IV가 필요하다. IV 자체는 기밀 데이터가 아니므로(비밀키가 중요함), 암호문 배열 맨 앞에 IV를 이어 붙인 후 통째로 Base64 인코딩하여 DB에 문자열 하나로 깔끔하게 저장될 수 있도록 로직을 설계했다.
