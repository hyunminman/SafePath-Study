Dreamhack 'Web Hacking Basics' (XSS, CSRF)

1. 개요: HTTP의 한계와 인증의 필요성

웹 기반 통신(HTTP)은 기본적으로 무상태(Stateless) 성질을 가진다. 서버는 클라이언트의 이전 요청을 기억하지 못하므로, 매번 로그인 상태를 확인해야 하는 구조적 한계가 있다. 이를 해결하고 사용자의 상태를 안전하게 유지하기 위해 쿠키, 세션, 토큰 등의 인증 메커니즘을 사용한다.

2. 인증 방식 비교 (Cookie vs Session vs Token)

2.1. 쿠키 (Cookie)

개념: 브라우저(클라이언트) 단에 저장되는 텍스트 데이터.

동작 원리: 서버가 응답 시 Set-Cookie 헤더를 통해 브라우저에 저장시키면, 이후 동일 도메인 요청 시 브라우저가 쿠키를 자동으로 동봉하여 전송한다.

보안 한계: 중요 정보(비밀번호 등)를 평문으로 담을 경우, 자바스크립트나 네트워크 패킷 스니핑으로 쉽게 탈취될 수 있어 단독 인증 수단으로는 부적합하다.

2.2. 세션 (Session)

개념: 중요한 회원 정보는 서버의 메모리나 DB에 저장하고, 클라이언트에게는 해당 정보를 식별할 수 있는 무작위 문자열인 '세션 ID'만 쿠키로 발급하는 방식.

장점: 클라이언트는 유의미한 데이터를 가지지 않아 정보 유출 관점에서 비교적 안전하며, 서버에서 특정 사용자의 세션을 강제로 만료시킬 수 있다. (Stateful)

단점: 동시 접속자가 증가하면 서버 메모리 부하가 커진다. 다중 서버(Scale-out) 환경에서는 세션 불일치를 해결하기 위한 별도의 세션 스토리지(Redis 등) 구축이 필요하다.

2.3. 토큰 (JWT - JSON Web Token)

개념: 인증 정보를 암호화된 토큰 문자열 자체에 담아 클라이언트에게 발급하는 방식. Header, Payload, Signature로 구성된다.

장점: 서버가 사용자 상태를 저장할 필요가 없어(Stateless) 서버 확장에 유리하다. Signature를 통해 데이터 변조 여부를 서버가 자체적으로 검증할 수 있다.

단점: 한 번 발급된 토큰은 유효기간이 끝날 때까지 서버에서 강제 무효화하기 어렵다. 이를 보완하기 위해 수명이 짧은 Access Token과 수명이 긴 Refresh Token 구조를 병행하여 사용한다.

3. 웹 해킹 기초 (Web Hacking Basics)

인증 수단(세션 ID, 토큰)을 타겟으로 하는 대표적인 클라이언트 사이드 공격 및 방어 기법을 정리한다.

3.1. XSS (Cross-Site Scripting)

공격 원리: 게시판 등 사용자 입력이 가능한 곳에 악성 자바스크립트 코드를 삽입하여, 다른 사용자가 게시글 열람 시 브라우저에서 스크립트가 실행되도록 하는 공격.

피해: 실행된 스크립트가 피해자 브라우저의 document.cookie를 읽어 공격자 서버로 전송하면 세션 하이재킹이 발생할 수 있다.

방어 대책 (Mitigation):

HTML Entity Encoding: 입력값 검증을 통해 <script> 등의 특수 태그를 일반 문자로 치환한다.

HttpOnly 속성 적용: 서버에서 인증 쿠키 발급 시 HttpOnly 옵션을 부여하면, 브라우저의 자바스크립트에서 해당 쿠키에 접근할 수 없어 XSS를 통한 탈취를 차단할 수 있다.

3.2. CSRF (Cross-Site Request Forgery)

공격 원리: 피해자가 특정 사이트에 로그인되어 있는 상태(유효한 인증 쿠키 보유)를 악용한다. 조작된 링크나 폼을 클릭하도록 유도하여, 피해자 몰래 패스워드 변경이나 결제 요청을 서버로 전송하게 만든다.

피해: 브라우저가 특정 도메인으로 요청 시 쿠키를 자동으로 포함하는 성질을 이용하므로, 사용자 의도와 무관한 기능이 강제 실행된다.

방어 대책 (Mitigation):

SameSite 쿠키 속성: 쿠키에 SameSite=Lax 또는 Strict를 설정하여, 타 도메인(Third-party)에서 시작된 요청에는 쿠키가 전송되지 않도록 방어한다.

CSRF Token: 요청 폼마다 예측 불가능한 임의의 토큰을 포함시키고, 서버에서 이 토큰의 일치 여부를 검증한다.
