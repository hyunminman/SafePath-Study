웹 보안 기초: 입력값 검증과 시큐어 코딩 원리

학습일: 2026.07.26
주제: Zero Trust 모델 기반의 입력값 검증 한계 파악 및 Prepared Statement 동작 원리 분석
목표: 애플리케이션 취약점이 발생하는 근본적인 원인을 구조적으로 이해하고 방어 논리 정립

웹 해킹 공격 기법을 다루기에 앞서, 취약점이 발생하는 백엔드 설계의 근본적인 결함을 분석하고 이를 방어하기 위한 시큐어 코딩의 핵심 원칙을 정리하였다.

1. 입력값 검증 (Input Validation)과 Zero Trust

사용자의 입력 데이터를 처리할 때 발생하는 클라이언트 사이드 검증의 한계를 개발자 도구를 통해 검증하였다.

프론트엔드 검증의 한계 실습:

웹 페이지의 폼(Form) 입력 필드에 설정된 maxlength (글자 수 제한) 또는 required (필수 입력) 속성을 F12 개발자 도구의 Elements 탭에서 임의로 변조 및 삭제하였다.

[분석 결과] 프론트엔드 레벨에서 구현된 유효성 검사는 사용자 경험(UX)을 위한 장치일 뿐, 보안 방어책이 될 수 없음을 확인하였다. 클라이언트는 언제든지 HTTP 패킷(Proxy 툴)이나 DOM 조작을 통해 조작된 데이터를 서버로 전송할 수 있다.

Zero Trust 아키텍처 적용:

따라서 "클라이언트가 전송하는 모든 데이터는 이미 조작되었다"는 Zero Trust 전제를 바탕으로, 데이터의 무결성 및 유효성 검증은 반드시 백엔드 서버 로직에서 재수행되어야 함을 확인하였다.

2. 시큐어 코딩의 핵심: 파라미터 바인딩 (Prepared Statement)

SQL Injection 취약점을 원천적으로 차단하기 위한 Prepared Statement(준비된 구문)의 동작 원리를 취약한 코드 패러다임과 대조하여 분석하였다.

2.1. 취약한 쿼리 조립 방식 (String Concatenation)

구조: SELECT * FROM users WHERE id = ' + userInput + '

취약점: 애플리케이션이 쿼리의 논리 구조와 사용자의 입력 데이터를 문자열 형태로 단순 결합하여 데이터베이스로 전송한다. 이때 입력값에 SQL 예약어(' OR '1'='1)가 포함되어 있으면, 데이터베이스 파서(Parser)가 이를 데이터가 아닌 '명령어'로 해석하여 쿼리의 본래 논리가 파괴된다.

2.2. 안전한 쿼리 처리 방식 (Prepared Statement)

구조: SELECT * FROM users WHERE id = ? (이후 매개변수로 userInput 전달)

방어 원리: 1. 애플리케이션은 데이터가 비어있는 쿼리의 논리적 뼈대(?)만을 데이터베이스로 먼저 전송한다.
2. 데이터베이스는 이 뼈대를 미리 컴파일하여 실행 계획을 확정한다.
3. 이후 사용자의 입력값이 전달되면, 데이터베이스는 이를 컴파일된 쿼리의 특정 위치(?)에 바인딩한다.
4. 이때 입력값 내부에 어떠한 SQL 쿼리문이 존재하더라도, 파서는 이를 명령어가 아닌 단순 '텍스트(Literal)'로 취급하므로 인젝션 공격이 구조적으로 불가능해진다.

// 1. 취약한 방식 (문자열 결합)
const query = "SELECT * FROM users WHERE id = '" + userInput + "'";

// 2. 안전한 방식 (Prepared Statement)
const query = "SELECT * FROM users WHERE id = ?";
db.execute(query, [userInput]);

[학습 결론]
대부분의 애플리케이션 취약점은 개발자가 사용자의 입력 데이터를 신뢰하고, 이를 시스템 명령어(SQL, Shell, HTML/JS) 영역에 검증 없이 혼용할 때 발생한다. 입력값의 철저한 백엔드 검증과, 논리/데이터 공간의 엄격한 분리가 시큐어 코딩의 근간임을 이해하였다.
