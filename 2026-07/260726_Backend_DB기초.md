데이터베이스 CRUD 및 인증 아키텍처 분석

학습일: 2026.07.26
주제: SQL 기본 문법(CRUD) 및 세션(Session)/토큰(Token) 인증 구조 비교
목표: 백엔드 데이터 처리 원리 및 인증 아키텍처 이해를 통한 보안 취약점 발생 배경 파악

웹 애플리케이션의 핵심 비즈니스 로직은 백엔드 데이터베이스 조작과 사용자 인증 처리에서 발생한다. 효율적인 시큐어 코딩 및 보안 아키텍처 설계를 위해 데이터베이스 쿼리의 기본 구조와 서버 인증 방식의 차이를 분석하였다.

1. SQL 기본 문법 (CRUD) 구조 분석

데이터베이스 관리 시스템(DBMS)과 통신하기 위한 표준 언어인 SQL의 핵심 조작어(DML)를 웹 기반 시뮬레이터 환경에서 직접 테스트하고 그 역할을 분석하였다.

C (Create) - INSERT: 새로운 레코드를 생성한다. (예: 회원가입 폼 데이터 저장)

R (Read) - SELECT: 데이터를 조회한다. (예: 로그인 시 계정 일치 여부 확인, 게시글 목록 조회)

U (Update) - UPDATE: 기존 레코드를 수정한다. 반드시 WHERE 조건절을 동반하여 특정 레코드만 수정하도록 제어해야 한다.

D (Delete) - DELETE: 기존 레코드를 삭제한다.

[분석 결과 및 보안 관점]
SQL Injection 공격은 주로 WHERE 조건절의 논리를 우회하거나, UNION 연산자를 사용하여 의도하지 않은 SELECT 결과를 덧붙여 출력하게 만드는 방식으로 이루어진다. 백엔드에서 쿼리를 조립할 때 입력값을 검증하지 않으면 데이터베이스 엑세스 제어가 완전히 붕괴됨을 구조적으로 확인하였다.

2. 서버 인증 아키텍처 비교 (Session vs Token)

HTTP 통신의 무상태성(Stateless)을 극복하고 사용자의 로그인 상태를 유지하기 위한 두 가지 핵심 인증 아키텍처의 동작 방식과 장단점을 대조하였다.

2.1. 세션 (Session) 기반 인증

동작 원리: 사용자가 로그인하면 서버는 고유한 'Session ID'를 생성하여 서버 메모리(또는 DB/Redis)에 상태를 저장(Stateful)하고, 클라이언트에게 Session ID를 쿠키로 전달한다.

장점: 서버가 인증 상태를 중앙 통제하므로, 특정 사용자를 강제로 로그아웃 시키는 등의 제어가 용이하다.

단점: 대규모 트래픽 발생 시 다중 서버(Scale-out) 환경에서 서버 간 세션 상태를 공유(Session Clustering)해야 하는 아키텍처 복잡성이 증가한다.

2.2. 토큰 (Token / JWT) 기반 인증

동작 원리: 사용자가 로그인하면 서버는 서명된 '토큰'을 발급하여 클라이언트에게 전달한다. 서버는 상태를 저장하지 않으며(Stateless), 이후 요청이 올 때마다 토큰의 서명 유효성만 검증한다.

장점: 서버가 상태를 보관하지 않으므로 로드밸런싱 환경에서 서버 확장이 매우 자유롭다.

단점: 발급된 토큰이 클라이언트에게 귀속되므로, 토큰이 탈취당할 경우 만료되기 전까지 서버에서 이를 강제로 무효화하기 어렵다.
